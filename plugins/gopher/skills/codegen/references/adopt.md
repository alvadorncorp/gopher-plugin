# Adopting an Ad Hoc Generator

Adoption turns a generator that someone ran once on a laptop into part of the
project contract: pinned, declared, marked, reproducible, and owned. It changes
project files, so it runs behind an approval gate.

## When adoption applies

- An artifact carries the code generation header but no discoverable producer.
- A producer exists but resolves from `PATH`, so its version is unattributable.
- A command lives in a developer's shell history rather than in a declared
  surface.
- An artifact is regenerated by hand on an informal cadence.

Each of these makes `check` report `BLOCKED` or an open hypothesis. Adoption is
the remediation that lets future checks reach a real verdict.

## The adoption steps

| Step | What it establishes | Where it lands |
|---|---|---|
| 1. Pin the generator | The output can be attributed to one version | `tool` directive in `go.mod`, or `go run <module>@<version>` in the command |
| 2. Declare the command | There is one authoritative invocation | a `//go:generate` line, a Makefile target, or a registry config |
| 3. Add the header | Humans and tools can tell the artifact is generated | the first comment block of each artifact |
| 4. Make regeneration reproducible | Two runs from identical inputs agree | the generator, the inputs, and the controlled environment |
| 5. Record provenance | A future check has something to compare against | the provenance record from `references/provenance.md` |
| 6. Record the owner | Someone is accountable for the generator | the project's ownership convention |
| 7. Verify by a fresh check | The adoption actually holds | a `check` run reaching `FRESH` |

Run the steps in order. A declared command with no pin still produces
unattributable output, and a pin with no declared command still leaves the
invocation to memory.

## Pinning

Prefer the mechanism the project already reviews:

```bash
go get -tool golang.org/x/tools/cmd/stringer@v0.30.0
go tool stringer -type=Pill
```

For a generator the project would rather not add to its module graph, an
explicit versioned invocation inside the declared command is the next best pin:

```go
//go:generate go run golang.org/x/tools/cmd/stringer@v0.30.0 -type=Pill
```

Both forms express the version in a reviewed file. Obtaining the generator stays
with the project's own dependency workflow; this skill records the exact pin the
project would need and stops there.

## Adding the header

The header goes before the first non-comment, non-blank text in the artifact and
matches `^// Code generated .* DO NOT EDIT\.$` exactly. Prefer having the
generator emit it, so every future run reproduces it. Adding it once by hand to
an existing artifact is acceptable only when the same run also teaches the
generator to emit it; otherwise the next regeneration drops it again.

## Removing nondeterminism

Adoption is incomplete while two runs disagree. Work through the drift table in
`references/reproduction.md`, and route each generator-side cause — unsorted map
iteration, embedded timestamps, embedded absolute paths, random identifiers — to
`gopher:developer` as a defect with the two differing outputs as evidence.

## The approval gate

Adoption edits `go.mod`, build files, declared commands, and artifact headers,
so `authorization_gate` is `approval-required` before any edit. Present the
proposed pin, the proposed declared command, the artifacts that gain a header,
and the files each step touches.

When approval is granted, apply the steps, then run a fresh `check` and report
the resulting state. When approval is declined, report the adoption plan
unchanged, keep the gate closed, and leave the current state as the answer. A
declined adoption is a complete result with a recorded plan.
